## 一、总体结论

先直接回答站主最关心的四件事。

### 1. 有没有漏洞？——没有发现可利用的漏洞，安全基本面是好的

全站 innerHTML 与 markdown 渲染的数据源全部是仓库内静态数据（js/articles.js / js/projects.js），`?post=` 深链只与静态数组做精确比对后才使用，搜索高亮先转义再加固定的 `<mark>` 标签。审计未发现可利用的 XSS、DOM 注入或开放重定向，也未发现任何密钥/令牌泄露；Service Worker 采用标准的 skipWaiting + 版本清理策略，prefetch 消息仅接受同源可控地址。

存在的是「防御深度」层面的缺口（均为 low）：markdown 渲染结果未经消毒直接写入 innerHTML（SEC-4 / ATK-2），文章卡片用内联字符串拼接 onclick、且现有转义方式不适配 JS 字符串上下文（SEC-3 / ATK-2）。这些在当前纯静态数据下不可被利用，但 README 已规划未来接入 giscus/Formspree 等外部内容，届时会立即升级为实际 XSS 面，建议提前补上。

唯一一个 medium 级的功能性缺陷在 Service Worker：导航缓存写入不校验响应状态（ATK-1），一条坏链接或他人分享的演示页链接就能把离线兜底首页换成 404 页或演示页。它不算传统安全漏洞，但直接击穿 sw.js 文件头自己宣称的「断网也能读手记和小说」这一核心卖点。

### 2. 会不会被人恶意攻击？——攻击面很小，真正要处理的只有一件事

线上实际为零第三方外链脚本：不蒜子已于 2026-09-30 从代码中移除，只剩 README 还写着旧文案；全部 git 历史无凭证泄漏；URL 参数只做数据查找、无注入路径。站外攻击者能做的事情非常有限。

需要处理的真实问题只有 ATK-1（SW 导航缓存投毒，medium）。其余均为低危的仓库卫生与加固项：全站无 CSP / iframe 防护（ATK-6）、十余个开发脚本连同本机绝对路径被 Pages 公开提供（SEC-1 / ATK-4）、.agent/ 六个技能文档违背 gitignore 意图被 git 跟踪（SEC-2 / ATK-3，复核实测其并未进入 Pages 发布产物）、同源媒体可被第三方热链刷 GitHub Pages 的 100GB/月软带宽上限（ATK-7）。

### 3. 很多人同时访问会不会卡？——服务端不会卡；决定体验的是每个访客被自动塞了多少字节

GitHub Pages + Fastly 纯静态分发，多人同时访问不会互相拖慢。「卡不卡」只取决于单个访客要传输多少字节：

- **冷访客关键路径本身很克制**：实测约 370KB（gzip 后 HTML 19.6KB + 4 个阻塞 CSS 21.0KB + 10 个 defer JS 约 74KB + 头像/封面/海报约 204KB，约 22 个请求），无阻塞 JS、零外链；视频 preload="none"、音乐 HTML 层 preload="none"；字体单文件 48KB woff2 + swap。
- **但自动化传输失控，把冷首访总传输推到约 6.3–7.0MB**：进站未点播就开始缓冲首曲 4.03MB 并被 SW 全量写入缓存（PERF-1 / PERF-2，最坏情况浏览器与 SW 各下一遍、2×4MB）；SW 预缓存清单约 1.9MB 不分设备档，手机访客白下 three.module.min.js 691,648 字节（PERF-3）；桌面档另有 three 动态加载。对按流量计费的手机用户这是实打实的损失——这就是「很多人访问会不会卡」的唯一实质答案。
- **第二次访问起走 SW 缓存，流量趋近于零。**

注：以上结论基于逐文件体积实测与源码精读，未做浏览器级 LCP 实测（见第四节）。

### 4. 文案有什么欠缺？——整体质量高，主要欠账是「文档和界面文案没跟上站点迭代」

正文无硬伤、语气统一（克制口语的编辑风）；提取码、版本号、产品数字等关键事实在 index.html 与 projects.js 之间逐字一致；RSS/sitemap 与文章数据同步。问题集中在少数界面文案与 README 承诺未随迭代更新：搜索面板有点击无反应的死条目（COPY-2）、404 页还说「三个小工具」而主站已是 6 张产品卡（COPY-3）、README 仍承诺已移除的不蒜子统计（COPY-4，与 SEC-5/ATK-5/PERF-5 四条同源）、README 还在教用户删除已不存在的示例条目（COPY-5）、演示页残留旧假数据且与主站口径冲突（COPY-6）；另有一处正文漏字（COPY-1）与站点名「楠屿札记 / SevenJohn」口径不统一（COPY-7）。

#### ATK-1 ｜ SW 导航缓存无状态码校验，可被远程投毒离线兜底首页 ｜ medium ｜ verified
- **位置**：sw.js:187-198。
- **证据摘录**：sw.js:190-193 把任何导航响应无条件 `cache.put('./index.html', copy)`，整个分支无 `res.ok` 判断；对照同文件其他分支（:208 CSS/JS、:224 静态资源、:105 prefetch）全有校验，唯独导航分支缺失。fetch 对 4xx 也是 resolve 而非 reject，故 404 页同样入缓存；`./index.html` 与 install 预缓存的 `index.html` 在 Cache API 中归一为同一键，覆盖的正是离线兜底首页。
- **触发场景**：用户打开分享的 /cosmos-home.html 链接（200 照样覆盖），或访问任何不存在的 URL（404 入库）。此后所有离线导航拿到最后一次在线导航的内容，在线导航回首页即自愈。
- **修复建议**：cache.put 前加 `if (!res.ok) return res;`，且只在与导航 URL 匹配的键下写缓存——复核强调两者需同时做（仅挡 404 挡不住 200 的演示页覆盖）。复核注明：GitHub Pages 的 404 响应行为未在本环境实测，基于公开标准行为认知，但代码级证据已充分支持定性。

**总体评价**：服务端侧无并发瓶颈——GitHub Pages + Fastly 纯静态分发，多人同时访问不会互相拖慢，「卡不卡」只取决于单访客要传多少字节。实测冷访客关键路径约 370KB、约 22 个请求、无阻塞 JS、零外链，媒体与字体策略克制。真正的问题在单访客自动传输：进站未点播就缓冲首曲 4.03MB 并被 SW 全量入库、SW 预缓存约 1.9MB 不分设备档、three 桌面动态加载，冷首访总传输约 6.3–7.0MB——这是「很多人访问会不会卡」的唯一实质答案；二访起走 SW 缓存流量趋近于零。注：结论基于逐文件体积实测与源码精读，未做浏览器级 LCP 实测。

- **位置**：js/player.js:269-270。
- **证据摘录**：`audio.preload = 'auto'; audio.src = SONGS[current].src;`（其上注释 265-268 自述「改 auto 让首曲在页面加载期就缓冲到位」），覆盖了 index.html:982 的 `preload="none"`；restore()（player.js:459）在脚本尾部无条件执行、对所有访客生效，无需任何点击；实测 attention.mp3 = 4,226,950 B ≈ 4.03MB，歌单 11 首共 48,030,597 B ≈ 45.8MB。无任何流量/设备门控（触屏降档已于 2026-09-30 移除，手机流量用户在内）。

## 三、建议处理顺序

原则：verified 且 high/medium 排前。理由：这一档里触发门槛最低（每一次冷访问、每一条坏链接）、修复成本也最低（合计几行改动），而其余 medium 都是公开页面上读者可见的事实错误、改文案即可；low 项不构成现实风险，可随下次发版顺手清理。

**第一批：先修（high + 核心承诺被击穿，且是同一条链路）**

1. **PERF-2 + PERF-1 一起修（high；必须联动）**：先删 sw.js:141/146 两处 lazyPrefetch 自动通道，再调整 player.js:269 的 preload 策略。理由：100% 冷访问路径触发、每访客最坏 2×4MB 双重下载、对按流量计费的手机用户是真实损失、Cache Storage 可逐首累积至 46MB；两处合计几行改动。注意复核盲点：只改 preload 治标不治本，metadata 仍会经 Range→lazyPrefetch 通道继续全量下载。
2. **ATK-1（medium）**：sw.js:190-193 导航分支在 cache.put 前加 `if (!res.ok) return res;`，并只在与导航 URL 匹配的键下写缓存。理由：一行级修复，直接挽回 sw.js 自己宣称的「断网也能读手记和小说」核心卖点；点开一条坏链接或分享链接即触发，且用户难以察觉。

**第二批：medium，用户可见或移动端实损，半天内可清完**

3. **PERF-3**：CORE 预缓存瘦身（three 移出改运行时缓存、highlight 移出恢复真按需、删 cover-gameboost.jpg）——手机/跨境链路首访少下约 1.0MB 白重。
