### 问题：改完分区开不了机

刷机的动作拆开看很简单：把镜像文件写进对应的分区。麻烦的地方在于写完能不能开机。

给 K60 Pro 打第一个 root 补丁时，我按教程把修补好的镜像刷进了 boot 分区，重启之后什么都没发生——root 没装上，系统照常运行。换成 init_boot 才成功。那次既没报错也没提示，只是安静地没生效。

另一种情况更麻烦：机器能通电，但卡在厂商 logo 反复重启。这通常不是刷错了分区，是校验没过。

### 方案：先弄清楚信任链从哪开始

这里其实是两件事——镜像怎么进去，和进去之后系统凭什么认它。

**写进去这条路不止一条。** 平时用的是 fastboot，它跑在 bootloader 之上，前提是引导本身是好的。再往下还有一条：高通平台上的 9008 模式。它由 SoC 里固化的一段代码撑起来，设备在设备管理器里显示成 Qualcomm HS-USB QDLoader 9008。这时跑的是 Sahara 协议，PC 把编程器文件（prog_firehose_ddr.elf 这类）分段传进设备内存、校验、跳进去执行；编程器起来之后切成 Firehose 协议，往后所有读写分区、擦除、改分区表，都是一条 XML 命令换一个 ACK 或 NAK。因为它绕开了整个系统层，直接对着存储芯片操作，机器砖了也能救回来。

**认不认，看的是验证启动这条链。** Android 从 8.0 起用 AVB 2.0，这套设计把校验集中到一个地方：vbmeta 分区。里面存着各个分区的哈希值和签名。开机时 bootloader 只做一件事——验 vbmeta 自己的签名。验过了，它就相信 vbmeta 里写的哈希，再拿这些哈希去比对 boot、init_boot、dtbo 这些分区。system 和 vendor 这类大分区用哈希树（dm-verity），不只在启动时比一次，运行中也持续校验数据块。

**再叠上 Android 13 的分区改动。** 从 Android 13 起，配 GKI 内核的设备把通用 ramdisk 从 boot 分区里挪了出来，单独放进 init_boot。于是 boot 里主要装内核，init_boot 装第一阶段的 init 和启动脚本。这就是为什么同一个「刷 boot 拿 root」的动作，在新设备上要换成 init_boot。

几条连起来就清楚了：root 补丁改的是 init_boot 的内容，内容一变哈希就对不上，bootloader 拿 vbmeta 里存的旧哈希去比对，发现不匹配就拒绝启动。正确顺序是——改完分区必须重算哈希、重签 vbmeta，再刷回去。

#### 现代设备生态的四种真实锁态

后来接触的设备多了才发现，Android 设备的启动链早就不只是简单的「解开 BL 刷第三方」：

1. **真解锁设备**：像 K60 Pro，Bootloader（ABL）解锁标志被物理置位，放行未经签名校验的底层镜像。这状态会忠实写进底层属性（`ro.boot.flash.locked=0`，显示 orange 告警），硬件级 KeyMint 凭据也会判定为解锁状态。
2. **自签设备**：像联想拯救者 Y700（二/三/四代），厂商启动链信任公开的 AOSP testkey。只要用这套公开密钥给改动后的 `init_boot` 和 `vbmeta` 签名，机器在 Bootloader 保持原厂锁定的状态下就能验证通过，开机依旧显示安全绿标。
3. **假回锁设备（Fake Lock）**：像荣耀等彻底关闭官方 BL 解锁通道的高通平台机型。依靠底层高通漏洞临时提权后，在引导链极早期（早于系统和 TEE 读取并固化锁状态前）植入内存 payload（如 hnubl、gbl_root_canoe、efisp 补丁），改写内存中的锁标志为 `locked & green`。系统与硬件 TEE 误以为依然处于原厂锁定状态，同时正常加载修补过的内核。
4. **免解设备**：仅靠用户态或内核运行时提权（通常伴随 SELinux permissive），重启即失效，无法持久。

#### A/B 槽位与保留锁态 OTA 的底层闭环

在假回锁体系下，最危险的动作莫过于系统在线更新（OTA）。

官方 OTA 程序下载全量包后，会自动把新系统写入当前闲置的备用槽位（比如从当前活动槽 `_a` 写进备用槽 `_b`）。这一写，原厂未修改的 `ABL` 引导与原厂 `init_boot` 就会直接覆盖备用槽。

如果不做干预直接重启：
- 备用槽的原厂 ABL 会导致假回锁补丁失效；
- 官方内核不带任何 root 权限；
- 更严重的是，未打补丁的锁态与残留的分区状态冲突，极易引发启动死锁黑屏变砖。

因此，假回锁机型升级系统必须严格执行**双保险协同**：
- **引导与锁态归专用工具管**：官方更新安装完成后，**绝对不能点系统弹窗的立即重启**，先打开引导维护工具（如 `hnubl`），对备用槽位的 ABL 和 efisp 重新写入假回锁补丁；
- **内核权限归 KernelSU 管**：再打开 KernelSU 授权界面，点击「安装到未使用的槽位（OTA 后）」，把 root 补丁写入备用槽位的 `init_boot`；
- 两边都就绪后，再安全重启切槽。

### 核心难点与工程排障

1. **补丁要打对分区。** Android 13 + GKI 的机器打 init_boot，更早的布局打 boot。打错了不会报错，只会静默失效或者卡开机。判断方法很直接：看官方固件包里有没有 init_boot.img。
2. **补丁必须和系统版本对齐。** 系统一升级，原来那份修补镜像就作废了。我盘里留了十份修补镜像，时间跨度半年，基本都是跟着版本走的。
3. **改过分区就得处理校验。** 不重签 vbmeta 就要显式关掉校验，否则一样开不了机。
4. **A/B 双槽机型要看清当前在哪个槽。** 刷错槽位的结果是「刷了跟没刷一样」，很容易误判成方法不对。日常使用也千万不要无故去点「切换活动槽位」或在平时去点「安装到未使用的槽位」，那只会弄乱备用分区的状态。
5. **假回锁机型严禁直冲 OTA 重启。** 收到推送必须严格遵守「官方写入备用槽 ➔ 工具修补备用 ABL 锁态 ➔ KernelSU 修补备用 init_boot ➔ 重启切槽」的次序。
6. **persist 和 modem 要单独备份。** 前者存传感器标定数据，后者关系到信号和基带，这两个丢了不是恢复出厂能补回来的。
7. **9008 认不到设备，基本是硬件问题。** 驱动没装对、线只能充电不能传数据、用了前置 USB 口或 Hub 供电不足——排查「电脑无法识别设备」时，核心排查项通常集中在此三处。
8. **回锁的前提是内容和签名完全一致。** 签名对不上还硬锁，拿到的就是一台开不了机的设备。

### 结论

刷机的操作只有「把镜像写进分区」这一件事，但能不能开机取决于另一套东西：**验证启动的信任链从 vbmeta 开始，改了下游就必须回头改上游**。想明白这一层之后，很多看起来玄学的「刷完不开机」都能倒推出原因。

从真解锁、自签 testkey 到 ABL 假回锁，设备的玩法在演进，底层的规则却始终如一：谁掌握了启动链更早期的时序，谁就能定义设备的信任状态。而 9008 这条通道则是最后的兜底防线——只要硬件底层握手还在，多数砖机都能救回。
