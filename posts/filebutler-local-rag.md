### 背景：既要搜得快，又要整理得稳
整理日常文档、票据和代码目录时，找文件讲究越快越好，批量归档又最怕误移误删。落到软件设计上就是两个硬指标：搜索响应要在毫秒级，批量移动前必须先展示改动清单，并支持按批次一键回滚。

### 架构：双轨索引与快慢解耦
- **文件名 / 长文本 / 语法匹配**：走 SQLite 内置 FTS5 倒排索引，毫秒级出结果，支持 `ext:pdf`、`size:>100mb`、`dm:本周` 这类语法。
- **语义问答**：采用 bge-m3 构建稠密向量索引，**由后台线程在系统空闲时增量构建**，避免阻塞用户主线程操作。
- **文件重组安全流程**：规则或端侧模型生成整理预案 → 生成明确的移动计划清单 → 用户人工勾选确认 → 写入事务日志并原子执行。支持按批次整体撤销回滚。
- **防御性降级机制**：本地 Ollama 服务不可用时自动降级为规则整理与 FTS5 关键词检索，保证基础功能不受影响。

```python
# 双轨查询：精确检索第一轨，语义重排在下游
def search_files(cursor: sqlite3.Cursor, query: str, limit: int = 20) -> list[dict]:
    cursor.row_factory = sqlite3.Row
    sql = """
        SELECT path, size, modified_at, bm25(files_fts) AS rank
        FROM files_fts
        WHERE files_fts MATCH ?
        ORDER BY rank
        LIMIT ?
    """
    return [dict(row) for row in cursor.execute(sql, (query, limit)).fetchall()]
```

### 核心难点与工程排障
1. **避免启动时瞬时构建全盘向量索引。** 启动即触发大批量向量化会导致系统 I/O 与 CPU 瞬时过载，拖慢交互；改为由后台线程在系统闲置时增量扫描入库。
2. **语义检索不适合精确匹配。** 搜文件名、扩展名、大小这类精确条件，向量检索反而找不准——先让 FTS5 命中，再用语义排序。
3. **「撤销」不是把操作反过来做一遍。** 移动可能覆盖同名文件、目标盘可能写满、期间文件可能又被改过。所以回滚必须基于事务日志，不能靠重算。
4. **文件监听事件的抖动合并。** watchdog 监听大型目录树时，单次目录拷贝会触发高频重复事件，须引入防抖机制与批量合并处理。
5. **本地预览服务只监听本机回环地址。** 缩略图等内部 HTTP 服务只绑定 127.0.0.1（仅本机可访问），不监听 0.0.0.0（对局域网开放），避免同一网络下的其他设备读取个人文件。

### 结论
做本地文件工具，检索必须要快，整理必须要稳。大模型在本地是很好的辅助，但绝不能让它成为单点故障——模型离线时，常规的关键词搜索和按规则归档依然要正常可用，并且每一次文件移动都要能安全撤销。
